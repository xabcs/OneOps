## 任务:参照 soybean-admin-element-plus 重构本项目代码组织

### 参考项目

`/Users/mpm/Desktop/doc/go/OneOpsV2/OneOps/soybean-admin-element-plus`

请先阅读该参考项目的以下目录,理解其代码组织哲学:

- `packages/` (monorepo 子包,共性能力下沉)
- `src/components/` (advanced / common / custom 三层,严格不含业务)
- `src/views/` (文件路由,每个视图自包含: index.vue + modules/ + hooks/ + shared.ts)
- `src/store/modules/` (按领域拆分: app/auth/route/tab/theme)
- `src/hooks/` (business + common 两层)
- `src/service/` (api/ + request/ 分离)
- `src/layouts/` (base-layout/blank-layout + modules/)

### 重构目标

将本项目 `frontend3` 的代码组织对齐参考项目,重点解决:

1. **共性代码封装分层不清** —— 通用能力、领域能力、视图能力混在一起
2. **代码 tree 不统一** —— 部分视图用了 composables/,部分没有;components/ 混合原子设计与业务

## 强制规则

### 规则 1:四级共性代码分层(由下至上)

| 层级 | 位置 | 判定标准 | 示例 |
|---|---|---|---|
| L1 跨项目通用 | `packages/@sa/*` | 与业务无关、可在其他项目复用 | use-table, use-boolean, crypto, storage, axios 封装 |
| L2 应用通用 | `src/hooks/common/`, `src/utils/`, `src/components/common/` | 本项目内跨业务域复用,但不绑定具体业务 | echarts hook, form hook, validation, logger |
| L3 领域共用 | `src/components/<domain>/`, `src/hooks/business/`, `src/utils/<domain>-*` | 绑定具体业务域(k8s/cmdb/audit),但跨多个视图复用 | K8sPodsTable, useWorkloadActions, k8s-formatters |
| L4 视图私有 | `src/views/<view>/modules/`, `src/views/<view>/composables/`, `src/views/<view>/shared.ts` | 仅当前视图使用 | DeploymentTab, useWorkloadData |

**判定优先级**:先看能否上浮到 L1/L2(越通用越好),不能才下沉。禁止把 L4 代码放进 `src/components/` 或 `src/utils/`。

### 规则 2:components/ 严格去业务化

`src/components/` 只保留三类,**禁止存放业务组件**:

```
src/components/
├── advanced/    # 高级复合组件(基于 UI 库二次封装,如表头操作、列设置)
├── common/      # 通用容器/外壳(app-provider, full-screen, theme-schema-switch)
└── custom/      # 通用定制组件(svg-icon, button-icon, count-to)
```

业务组件必须迁移到:

- 跨视图复用的 → `src/components/<domain>/` (如 `src/components/k8s/`、`src/components/cmdb/`)
- 单视图专用 → `src/views/<view>/modules/`

**待迁移清单**(请逐一处理):

- `components/k8s/` → 保留(已是领域共用,符合 L3)
- `components/permission-matrix/` → 保留(领域共用)
- `components/features/cmdb/`、`components/features/monitoring/`、`components/features/terminal/` → 评估:若仅 1 个视图使用则下沉到该视图的 modules/;若跨视图则移至 `src/components/<domain>/`
- `components/atoms/`、`components/molecules/`、`components/organisms/` → 保留作为原子设计层,但需确认每个组件确实跨域复用;否则下沉
- `components/PermissionButton.vue`、`components/YamlEditor.vue` → 若跨域用则保留在 common/ 或 custom/;若仅特定域用则迁移

### 规则 3:utils/ 去领域化

`src/utils/` 只保留**与业务无关**的工具函数。领域工具迁移到对应位置:

```
src/utils/        # 保留: common, storage, agent, icon, service, validation, form-validation, file, logger, performance, error-handler
                  # 迁出:
                  #   k8s-formatters.ts → src/views/k8s/shared/k8s-formatters.ts (或 src/components/k8s/shared/)
                  #   content-theme.ts → src/theme/ 或 src/styles/
                  #   error-codes.ts → src/constants/business.ts 或 src/service/shared/
                  #   permission.ts → src/hooks/business/auth.ts 或 src/store/modules/auth/
```

### 规则 4:每个视图自包含(统一模板)

所有 `src/views/<domain>/<feature>/` 必须遵循:

```
src/views/<domain>/<feature>/
├── index.vue              # 页面入口,只做组装
├── modules/               # 该视图专用子组件(如 DeploymentTab.vue、LogDialog.vue)
├── composables/           # 该视图专用逻辑(如 useWorkloadData.ts、useWorkloadActions.ts)
├── shared.ts              # 该视图专用类型/常量/纯函数
└── types/                 # (可选)复杂类型单独放
```

**强制要求**:

- 单文件 index.vue 超过 200 行必须拆分到 modules/ + composables/
- 逻辑超过 100 行的 setup() 必须抽到 composables/
- 视图内不得直接调用 axios/alova,必须通过 `@/service/api/*`

**需要统一的视图**(请检查并补齐):

- `views/k8s/clusters/` (当前是平铺 5 个 .vue,需拆分为 index.vue + modules/)
- `views/k8s/resources/*/` (大量平铺 index.vue + detail.vue,需评估是否抽 composables)
- `views/cmdb/servers/` (已用 composables/ + components/ + types/,作为标准范本推广)
- `views/auth/*/` (多数为单 index.vue,需评估)

### 规则 5:store/ 按领域拆分

`src/store/modules/` 每个领域一个目录,内部结构统一:

```
src/store/modules/<domain>/
├── index.ts       # store 定义 + 导出
└── shared.ts      # (可选) 该 store 的类型与辅助函数
```

**禁止**:

- 在 store 中直接写业务组件逻辑
- 跨域 store 互相 import 内部状态(只通过 export 的 action/getter 交互)
- `src/store/` 根目录放散落文件(如当前 `permission-with-diagnostic.ts` 需归入 `auth/` 或新建 `diagnostic/` 模块)

### 规则 6:service/ 严格 api/request 分离

```
src/service/
├── api/
│   ├── <domain>.ts     # 按业务域组织(auth/k8s/cmdb/audit/monitoring/diagnostic/application-permission)
│   └── index.ts        # 统一导出
└── request/
    ├── index.ts        # 请求实例
    ├── shared.ts       # 拦截器、错误处理
    └── type.ts         # 请求/响应通用类型
```

**禁止**:在 `api/*.ts` 中写请求实例配置;在 `request/` 中写具体业务接口。
**例外**:`websocket.ts` 可保留在 `service/` 根目录,或迁至 `src/service/websocket/`。

### 规则 7:hooks/ 两层结构

```
src/hooks/
├── business/    # 业务相关(auth, captcha, 以及新增的 k8s/cmdb 等域 hook)
└── common/      # 业务无关(echarts, form, icon, router, table, vchart)
```

跨视图复用的业务 hook(如 `useWorkloadActions` 若被多个 workload 视图共用)应从 `views/k8s/workloads/composables/` 上浮到 `hooks/business/k8s/`。

## 执行步骤

请按以下顺序执行,每步完成后输出变更摘要:

### 步骤 1:盘点(只读,不改代码)

扫描 `src/` 全部目录,输出"共性代码分层违规清单"(L4 误放 L2/L3 的文件列表)。

**输出格式示例**:

| 当前路径 | 当前层级 | 应放置层级 | 应迁移路径 | 迁移原因 |
|---|---|---|---|---|
| `src/utils/k8s-formatters.ts` | L2 | L3 | `src/views/k8s/shared/k8s-formatters.ts` | 绑定 k8s 业务域 |
| `src/components/features/terminal/SSHTerminal/index.vue` | L3 | L4 | `src/views/<使用它的视图>/modules/SSHTerminal.vue` | 仅一个视图使用 |

**完成后停止,等待用户 review 清单后再继续步骤 2。**

### 步骤 2:components/ 清理

按规则 2 迁移业务组件,更新 `components/index.ts`。

**操作要点**:

1. 识别 `src/components/` 下所有业务组件
2. 判定每个组件是 L3(跨视图)还是 L4(单视图)
3. L3 组件迁移到 `src/components/<domain>/`
4. L4 组件迁移到对应 `src/views/<view>/modules/`
5. 更新 `src/components/index.ts` 的导出
6. 批量修复所有引用该组件的 import 路径
7. 运行 `pnpm typecheck` 验证

**输出"迁移前 → 迁移后"映射表**。

### 步骤 3:utils/ 清理

按规则 3 迁移领域工具。

**操作要点**:

1. 识别 `src/utils/` 下所有领域相关文件
2. 按规则 3 迁移到对应位置
3. 批量修复 import 路径
4. 运行 `pnpm typecheck` 验证

**输出"迁移前 → 迁移后"映射表**。

### 步骤 4:views/ 统一

按规则 4 为每个视图补齐 `modules/composables/shared.ts` 结构。

**操作要点**:

1. 扫描所有 `src/views/<domain>/<feature>/index.vue`
2. 对超过 200 行的 index.vue:
   - 提取子组件到 `modules/`
   - 提取业务逻辑到 `composables/use<Feature>.ts`
   - 提取类型/常量到 `shared.ts`
3. 对平铺多文件的视图(如 `k8s/clusters/`):
   - 将 `ClusterDetail.vue`、`ClusterNodes.vue` 等迁入 `modules/`
   - 新建 `index.vue` 作为入口组装
4. 每个视图处理完后运行 `pnpm typecheck` 验证

**输出每个视图的"重构前结构 → 重构后结构"对比**。

### 步骤 5:store/service/hooks 校验

按规则 5/6/7 修正位置。

**操作要点**:

1. `src/store/`:
   - 检查根目录散落文件(如 `permission-with-diagnostic.ts`),归入对应领域模块
   - 确认每个领域模块有 `index.ts`,复杂的有 `shared.ts`
2. `src/service/`:
   - 确认 `api/` 与 `request/` 严格分离
   - 评估 `websocket.ts` 是否需迁入 `service/websocket/`
3. `src/hooks/`:
   - 检查 `common/` 是否混入业务 hook
   - 检查 `business/` 是否需按域分子目录(如 `business/k8s/`、`business/cmdb/`)
4. 运行 `pnpm typecheck` 验证

**输出变更摘要**。

### 步骤 6:导入路径修复与最终验证

**操作要点**:

1. 全局扫描所有 `.ts`、`.vue` 文件的 import 语句
2. 修复因文件迁移导致的 broken import
3. 运行 `pnpm typecheck` 直至无报错
4. 运行 `pnpm lint` 直至无报错
5. 运行 `pnpm dev` 验证应用可正常启动

**输出最终验证报告**:

- typecheck 结果: ✅/❌
- lint 结果: ✅/❌
- dev 启动结果: ✅/❌
- 总变更文件数: N

## 使用说明

1. **分步执行**:本提示词分 6 步,建议每次只让 AI 执行其中 1-2 步,避免一次性改动过大难以审查。
2. **先盘点后动手**:第 1 步"盘点"只输出违规清单不修改代码,可以先 review 这份清单,确认判定标准是否符合预期,再让它执行后续步骤。
3. **可调参数**:
   - 视图拆分阈值(200 行/100 行)可根据团队偏好调整
   - `components/` 是否保留原子设计层(atoms/molecules/organisms)可按需删除规则中相关条款
   - 领域划分(k8s/cmdb/audit/auth/monitoring/terminal)可按实际业务域增删
4. **风险点**:跨文件 import 路径修复是最大风险,务必在每步后跑 `pnpm typecheck`,不要全部改完再验证。

## 验收标准

重构完成后,需满足以下全部条件:

- [ ] `src/components/` 下无业务组件,仅保留 advanced/common/custom/(+可选原子设计层 +领域共用子目录)
- [ ] `src/utils/` 下无领域专用工具,仅保留业务无关工具
- [ ] 所有 `src/views/<domain>/<feature>/` 遵循 `index.vue + modules/ + composables/ + shared.ts` 模板
- [ ] 所有 index.vue 不超过 200 行
- [ ] 所有 setup() 逻辑不超过 100 行,超过部分抽到 composables/
- [ ] `src/store/modules/` 每个领域一个目录,根目录无散落文件
- [ ] `src/service/api/` 与 `src/service/request/` 严格分离
- [ ] `src/hooks/common/` 无业务 hook
- [ ] `pnpm typecheck` 通过
- [ ] `pnpm lint` 通过
- [ ] `pnpm dev` 可正常启动
