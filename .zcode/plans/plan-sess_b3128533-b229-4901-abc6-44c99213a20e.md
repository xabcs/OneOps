# backend3 接入 Swagger 实施计划

## 目标
为 backend3(Go + Gin + GORM)接入 Swagger / OpenAPI 文档,基于 `swaggo/swag` 生态,通过代码注释自动生成。覆盖全部 249 个 HTTP 接口,UI 仅在开发/staging 环境开放。

## 技术选型
- `github.com/swaggo/swag` —— CLI 工具,扫描注释生成 `docs/` 下的 OpenAPI JSON/YAML
- `github.com/swaggo/gin-swagger` —— Gin 中间件,提供 Swagger UI 路由
- `github.com/swaggo/files` —— 嵌入式 swagger.json 服务

理由:Gin 生态的事实标准;纯注释驱动,零运行时反射;生成的 `docs/swagger.json` 可直接喂给前端或其他工具链。

## 环境注意
项目 `go.mod` 声明 `go 1.26.0`,本机工具链为 1.24.3,且 toolchain 自动下载被 `GOSUMDB=off` 阻断。所有 `go` 命令需带 `GOTOOLCHAIN=local`。会在 `Makefile` 和文档中固化这一点。

## 实施步骤

### 阶段 1:基础设施(框架 + 生成流水线)

**1.1 新增依赖**
- `go get github.com/swaggo/swag/cmd/swag`(CLI)
- `go get github.com/swaggo/gin-swagger`、`github.com/swaggo/files`(运行时库)
- `go get github.com/swaggo/swag`(annotation 解析库,被 gin-swagger 间接需要)
- 全部用 `GOTOOLCHAIN=local go get ...`,更新 `go.mod`/`go.sum`

**1.2 新建 `docs/` 包(API 元信息)**
- 新建 `backend3/docs/docs.go`(由 swag init 生成,不手写)
- 新建 `backend3/docs/swagger.json`、`backend3/docs/swagger.yaml`(生成产物,提交入库)
- 在 `cmd/api/main.go` 顶部添加包级 API 元信息注释(general API info):
  ```
  // @title           OneOps API
  // @version         1.0
  // @description     OneOps 一体化运维平台后端 API
  // @host            localhost:端口(从配置读)
  // @BasePath        /api
  // @securityDefinitions.apikey BearerAuth
  // @in header
  // @name Authorization
  ```
- 在 `main.go` import `_ "oneops/backend3/docs"`(注册生成的 spec)

**1.3 挂载 Swagger UI 路由(仅开发环境)**
- 在 `routes/router.go` 的 `SetupRoutes` 末尾,依据 `cfg.App.Environment != "production"`(及 `cfg.App.Debug`)条件注册:
  ```go
  r.GET("/swagger/*any", ginSwagger.WrapHandler(swaggerFiles.Handler))
  ```
- 为避免 main.go 与 routes 之间传参复杂化,采用「在 main.go 拿到 cfg 后,通过新增的 `routes.SetupSwagger(r, cfg)` 入口注册」,保持 `SetupRoutes` 职责单一。

**1.4 新建 `Makefile`(固化生成流程)**
- 目标 `swag-init`:`GOTOOLCHAIN=local swag init -g cmd/api/main.go -o docs --parseDependency --parseInternal`
- 目标 `swag-fmt`:`swag fmt`(统一注释格式)
- 目标 `build`:`swag-init` + `go build`
- 目标 `run`:`swag-init` + `go run`
- 在根目录或 `backend3/` 下放一份简要 `SWAGGER.md` 说明使用方式。

### 阶段 2:全量接口注释(249 个 handler)

为每个 handler 函数上方添加 swag 注释块。统一模板(中文摘要,符合项目既有注释风格):

```go
// GetUser godoc
// @Summary      获取用户列表
// @Description  分页获取系统用户列表,支持按用户名/昵称/邮箱/状态搜索
// @Tags         系统管理/用户
// @Accept       json
// @Produce      json
// @Param        username  query     string  false  "用户名"
// @Param        page      query     int     false  "页码"  default(1)
// @Param        pageSize  query     int     false  "每页数量"  default(20)
// @Success      200       {object}  utils.Response{data=dto.PageResult{list=[]modelsystem.User}}
// @Failure      200       {object}  utils.Response  "业务错误(code=400)"
// @Router       /system/users [get]
// @Security     BearerAuth
```

**统一约定**
- `@Tags`:按模块分组 —— 系统管理-菜单/角色/用户/权限/应用授权、CMDB-服务器/分组/标签/凭证/Agent/堡垒机会话、K8s-集群/工作负载/网络/配置/终端/诊断、审计日志、监控告警/通知/报表、认证。
- 响应类型:统一用 `utils.Response` 作外层;`data` 用 `dto.PageResult` 或具体 model/Request 结构;无法精确建模的内联 `gin.H`(如 k8s diagnostic/permission、监控部分接口)用 `object` + 文字描述。
- 认证:`@Security BearerAuth`(除 `/login`、`/route/getConstantRoutes`、agent heartbeat、WebSocket 外)。
- 路径前缀:`@Router` 写完整路径(不含 `/api`,因 BasePath 已设),如 `/system/users`、`/cmdb/servers`、`/k8s/clusters`。

**特殊接口处理**
- **WebSocket**(2 个:k8s terminal `/k8s/terminal/ws`、monitoring `/monitoring/ws`):用 `@Success 101` + 描述协议;token 作为 query 参数注明。
- **CSV 下载**(2 个:`/audit/login-logs/export`、`/audit/operation-logs/export`):`@Produce text/csv`、`@Success 200 {file} binary`。
- **map[string]interface{} 请求体**(CMDB update 系列):用对应 model 结构建模,描述「部分字段更新」。
- **service 包类型作为请求体**(monitoring AlertRule/NotificationChannel、cmdb AgentHeartbeatData):在 controller 侧或新建 `pkg/dto` 结构做 swagger 友好建模,避免直接引用 service 层类型导致循环依赖。优先方案:为这些少量接口在 controller 文件内定义带 json tag 的请求 DTO 结构。

**执行顺序**(按依赖复杂度从低到高,每完成一个模块即可独立验证)
1. system 模块(auth/menu/role/user/permission/route)—— 30 个接口
2. audit 模块 —— 7 个接口(含 2 CSV)
3. cmdb 模块(server/group/business/room/tag/ssh_credential/asset_change/agent/attribute/bastion)—— ~60 个接口
4. monitoring 模块 —— 20 个接口(含 1 WS)
5. k8s 模块(cluster/permission/resource×9/terminal/diagnostic)—— ~70 个接口(含 1 WS)
6. authorization 模块(application_permission)—— 38 个接口

每完成一个模块后运行 `swag init` 验证注释无解析错误。

### 阶段 3:验证与收尾

**3.1 编译与生成验证**
- `GOTOOLCHAIN=local make swag-init` 成功,`docs/swagger.json` 生成
- `GOTOOLCHAIN=local go build ./...` 通过
- `docs/swagger.json` 中 path 数量 ≈ 路由表总数(核对关键模块)

**3.2 运行时验证**
- 启动服务,浏览器访问 `http://localhost:<port>/swagger/index.html`
- 抽查:登录接口可调试、鉴权接口填入 token 后可调试、CSV/WebSocket 接口展示正常

**3.3 文档**
- 新建 `backend3/SWAGGER.md`:如何生成、如何加注释、环境约束(GOTOOLCHAIN=local)
- 在 `API_SPECIFICATION.md` 顶部加一行指向 Swagger UI 的说明

---

## 不在本次范围
- 不重构现有 controller 逻辑;仅在函数上方加注释、必要时新增请求 DTO 结构。
- 不改路由路径或响应封装格式。
- 不引入 OpenAPI 3.0(swaggo 当前稳定输出 Swagger 2.0,够用;升级另议)。

## 风险与对策
- **风险**:249 个接口注释工作量大、易遗漏。**对策**:按模块分批,每批 `swag init` 验证;用脚本核对「routes 表 vs swagger.json path 数」查漏。
- **风险**:本机 toolchain 版本不匹配导致 `go get` 失败。**对策**:全程 `GOTOOLCHAIN=local`;若依赖确实需要 1.26,退而在容器或 CI 环境生成 docs,本机仅做注释。
- **风险**:内联 `gin.H` 响应无法强类型建模。**对策**:降级为 `object` + 描述文字,不影响 UI 可用性。
