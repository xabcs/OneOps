## 八、常见问题排查

### 1. initContainer Exit 1
```sh
# 看具体哪一步失败
kubectl logs -n test <pod> -c arthas-agent

# 可能原因：
# - 镜像没重新 build（arthas.properties 还是注释状态）→ docker build + push
# - arthas-core.jar 不存在 → Dockerfile 的 unzip 路径错
# - 镜像 tag 没变但内容变了 → imagePullPolicy: Always（已配置）
```

### 2. agent online: false
```sh
# 检查 K8s Service 是否可解析
kubectl exec -n test <pod> -- nslookup arthas-tunnel.test
kubectl exec -n test <pod> -- sh -c 'nc -zv arthas-tunnel.test 7777'

# 检查 Arthas 日志
kubectl exec -n test <pod> -- cat /root/logs/arthas/arthas.log | tail -50

# 常见原因：
# - tunnel-server 与 agent 版本不匹配（必须都是 4.1.8）
# - K8s Service arthas-tunnel 不存在或端口不对
# - agent 没读到 tunnelServer 配置（检查 env/properties）
```

### 3. websocket panic: repeated read on failed websocket connection
- 根因：gorilla/websocket v1.5.x 在 ReadMessage 出错后再次 Read 会 panic
- 修复：collectOutput 出错直接返回，不 continue 循环（已修复）
- 上游原因：agent 不在线时 WS 会话立即被 tunnel-server 断开

### 4. WS 会话超时（agent 在线但命令执行超时）
- 根因：gorilla/websocket 的 SetReadDeadline 超时后会把错误写入 c.readErr，
  后续所有 ReadMessage 都会返回旧错误。旧代码连续调用 collectOutput（先收集
  banner 再收集命令输出），第一次 idle 超时污染 readErr，第二次全部返回旧错误
- 修复：collectOutput 重写为 goroutine 阻塞读 + select channel 做 idle 超时，
  不使用 SetReadDeadline，避免 readErr 污染（已修复）
- 验证：wscat 直连正常但平台超时 → 问题在平台代码而非 agent

### 5. 后端 9443 未监听
- webhook 是懒启动：治理页启用开关后才拉起 TLS server
- 检查：ss -tlnp | grep 9443
- 证书由 ensureCert() 自动生成自签证书 + 同步 caBundle 到 MWC

### 6. agent 注册表 success:true 但实际不在线
- 现象：tunnel-server API 返回 success:true，但 WS 会话超时
- 根因：success:true 只表示 agentId 在注册表里，不代表当前 WS 长连接活跃
- 修复：ExecuteOneShot 执行前实时调 CheckAgentOnline 探测，更新 DB online 状态
- 探测失败时降级用 DB 旧值 + 警告日志

### 7. 命令输出只有 banner（thread -n 5 返回 banner 而非线程表格）
- 现象：执行 `thread -n 5`，耗时 3.22s，返回的 output 是 Arthas banner
  （logo + wiki/version 元信息 + `[arthas@1]$`），没有线程表格
- 根因：banner collect 的 idleTimeout=2s 太短。Arthas agent 在 WS 会话建立后
  需要初始化（加载类、启动 telnet），banner 首条消息可能在 2s 之后才到达。
  banner collect 在 banner 到达前就 idle 超时返回空（error 被 `_` 丢弃），
  随后 Arthas 发送的 banner 被 reader 放入 channel，发送命令后 command collect
  从 channel 读到 banner，把 banner 当作命令输出返回
- 时间线：3.22s = 2s（banner collect 空等 idle）+ 1.22s（command collect 收到
  banner 后连接断开或 idle 触发返回）
- 修复：collect 增加 stopMarker 参数，检测到 `[arthas@` 提示符立即返回（这是
  Arthas 就绪/命令完成的可靠标志）。banner collect 改为 idle 5s + 检测提示符，
  command collect 改为 idle 8s + 检测提示符，并增加 trimArthasPrompt 剥离
  末尾提示符
- 关键代码：diagnostic_service.go `collect()`、`runCommandOverTunnel()`、
  `trimArthasPrompt()`

### 8. 命令执行超时（banner 收到但命令无响应）
- 现象：banner collect 成功（1312 字节，含 [arthas@ 提示符，217ms），
  command collect 8s idle 超时，outputLen=0，错误"命令执行超时"；
  wscat 直连输入命令同样无响应
- 根因（已读官方源码确认）：**Arthas WS 会话输入/输出两个方向协议不同**
  - 输出方向（agent→平台）：纯文本（banner/命令结果都是纯文本透传）
  - 输入方向（平台→agent）：JSON 协议，termd HttpTtyConnection.writeToDecoder：
    - {"action":"read","data":"<用户输入>"}：data 可一次带整条命令 + \r
    - {"action":"resize","cols":120,"rows":40}
    - 纯文本帧在 agent 端 JSON.parseObject 失败，catch 后直接 return
      **静默丢弃**，所以命令无响应也无错误
  - 源码链路：tunnel-server RelayHandler 纯转发 → agent ForwardClient →
    LocalChannel → arthas core TtyWebSocketFrameHandler.channelRead0 →
    writeToDecoder(msg.text())
  - 源码位置：github.com/alibaba/termd 的 HttpTtyConnection.java（类注释
    明确写了 json messages 协议）
- 修复：命令发送改为 {"action":"read","data":"<command>\r"} 一条 JSON 消息，
  reset 同样
- 关键代码：diagnostic_service.go `runCommandOverTunnel()` 中 `sendRead()`
- 同源问题：交互式终端 WS 桥（controller/k8s/diagnostic_ws.go）同样把用户
  输入以纯文本发给 tunnel，导致"终端不能键入"，已一并改为 JSON read 协议；
  resize 消息也由忽略改为转发（termd 支持 {"action":"resize","cols":..,"rows":..}，
  表格按终端宽度渲染不折行）

### 9. 会话与诊断目标解耦（交互设计变更）
- 原设计：专家终端 watch currentAgent，切换左侧目标强制断开会话
  （"已切换诊断目标，会话已断开"），与 Arthas 官方多客户端语义不符
  （官方 quit 只影响当前客户端，多客户端可并发 attach 同一进程）
- 新设计（对齐 Arthas 官方语义 + 通用终端产品惯例）：
  - ExpertTerminalPanel：会话建立时快照目标（sessionAgent），此后切换左侧
    目标不影响进行中的会话；工具栏显示会话目标，目标不一致时提示
    "左侧已切换目标，会话保持"；断开仅由用户显式操作/连接异常触发
  - 场景跳转（autoCommand）：命令归属于左侧当前目标，若终端会话连在
    其他实例上则先断开再连命令目标（避免发错实例）
  - ScenarioPanel / CommandCatalogPanel：执行结果带"目标: <pod>"标记，
    切换左侧目标不清空已有结果，结果归属明确
- 效果：终端开着 watch/trace 监控时，可切到场景诊断执行 one-shot 命令、
  或切换其他实例查看信息，返回时会话仍活着
- 涉及文件：
  - frontend3/src/views/k8s/diagnostic/modules/ExpertTerminalPanel.vue
  - frontend3/src/views/k8s/diagnostic/modules/ScenarioPanel.vue
  - frontend3/src/views/k8s/diagnostic/modules/CommandCatalogPanel.vue
- 验证：vue-tsc 无 diagnostic 相关新增错误

### 10. thread -n 5 输出验证（JSON read 协议生效）
- 场景诊断执行 thread -n 5 成功返回 CPU Top 线程 + 完整堆栈，483ms
- 输出首线程为 arthas-command-execute（执行命令自身线程，正常现象）

### 11. webhook 静默不注入排查与修复（demo2 验证发现）
- 现象：demo2.yml（仅 label 的干净版）部署后 Pod 无 initContainer/env，无 FailedMutatingWebhook 事件
- 根因：治理页保存回调地址（9443→39443 端口映射变化）只写 DB 不更新 MWC，
  MWC 仍指向旧地址；apiserver 调不通 + failurePolicy=Ignore → 静默跳过注入
- 修复：SaveWebhookConfig 保存回调地址后调用 syncEnabledMWCs()，
  对所有已启用（MWC 存在）的集群自动 EnableWebhook 重建（url/caBundle 同步，
  host 变化时证书自动重签）；未启用集群不代为开启；同步失败仅警告不影响保存
- 效果：治理页改回调地址保存即生效，无需关闭再打开注入开关
- 代码：backend3/service/k8s/arthas_webhook.go `syncEnabledMWCs()`
- 验证：go build exit 0；治理页保存 39443 后 MWC url 应更新，
  rollout restart test-java2 后 initContainer=oneops-arthas-agent 被注入

### 12. agent 注册表保存失败（Error 1292: Incorrect datetime value '0000-00-00'）
- 现象：upsertAgentRecord 更新已有记录报错，created_at='0000-00-00 00:00:00'
- 根因：service 更新路径只回填 ID 不回填 CreatedAt，repository 用 Save()
  全字段更新，time.Time 零值被写成 '0000-00-00'，MySQL 严格模式拒绝
- 修复：UpsertAgent 更新路径改 Updates(map) 指定业务列（cluster_id/app_name/
  namespace/pod_name/agent_version/online/last_seen），不碰 created_at；
  ID=0 时 Create（GORM 自动维护时间戳）
- 代码：repository/k8s/diagnostic_repository.go `UpsertAgent()`
- 验证：go build exit 0；SyncAgents 后无 "保存 agent 注册信息失败" 警告

### 13. 独立 admission webhook 服务拆分（解决 ACK master 出网不通）
- 现象：MWC 指向正确后仍静默不注入；Fail 探针法（临时 failurePolicy=Fail +
  kubectl run）实锤 apiserver 回调 `https://60.191.116.75:39443/...`
  context deadline exceeded —— ACK 托管集群 master（托管面）无法出网到
  IDC 公网 IP（node 出网正常），URL 型 MWC 此路不通
- 方案：webhook 服务单独部署进目标集群（Deployment+Service），MWC 改用
  Service 型 clientConfig（istio-sidecar-injector 同构路径，apiserver →
  ClusterIP 必达）。不是 Operator：无 CRD/Informer/reconcile，纯无状态
  admission HTTP handler
- 变更清单（独立工程形态）：
  - arthas-webhook/（MsrePilot 独立工程，与 backend3/frontend3 平级，独立
    go module，仅依赖 gin+zap+k8s api 类型，无 DB/API 依赖树）：
    - main.go：env 读配置（ARTHAS_TUNNEL_WS/ARTHAS_INIT_IMAGE/端口/证书目录），
      bootstrapCert 证书保障 + gin TLS + /healthz + 优雅退出
    - inject.go：注入核心独立副本（常量 + shouldInject + buildInjectionPatch +
      handleAdmission），与 backend3 的 BuildInjectionPatch 双份维护、改动须同步
    - rotator.go：证书自签与轮转（首次自动签发/12h 巡检/轮转后即时更新 caBundle）
    - reconcile.go：MWC 生命周期控制器（意图与实现分离）——治理页启停只写
      意图（ConfigMap WEBHOOK_ENABLED），控制器双路径收敛：watch 意图变化
      秒级触发（快路径）+ 15s ticker 兜底（漂移自愈/watch 断线补偿）。
      enabled 建/修
      MWC（spec+caBundle 漂移自愈，带所有权 label oneops.io/managed-by=oneops），
      disabled 删 MWC，孤儿清理（label 匹配的非当前名 + 历史名 oneops-arthas-inject
      一次性收编——本次集群里的旧 MWC 会被自动删掉，无需手工）
    - Dockerfile：多阶段构建（golang:1.26-alpine → alpine:3.20 非 root），
      构建上下文即本目录，产物 < 20MB
    - msrepilot-deploy.yaml：test ns + RBAC（Secret/ConfigMap ns 级最小权限；
      MWC 集群级 get/list/create/update/delete——controller 化必要权限，
      范围自律靠所有权 label）+ ConfigMap（含 WEBHOOK_ENABLED 意图 key）+
      空 Secret（轮转器自动签发）+ Deployment（1 副本/HTTPS 探针）
      + Service 9443
  - backend3（只留管理面）：
    - arthas_webhook.go：
      - 治理页回调地址支持双格式：`svc://<ns>/<name>:<port>`（Service 型）/
        `https://...`（URL 型），parseSvcRef 智能识别
      - EnableWebhook：svc 模式只写意图（ConfigMap WEBHOOK_ENABLED=true）并
        轮询等待 msre-pilot 控制器收敛（≤20s，超时不算失败，最终一致）；
        URL 模式仍本进程直建 MWC（TLS server + 本地 ca.crt）
      - DisableWebhook：svc 模式写意图 false；URL 模式直接删 MWC
      - GetWebhookStatus：svc 模式读意图，URL 模式查 MWC 存在性
      - caBundleForWebhook/webhookClientConfig：svc 分支删除（职责移交控制器）
      - SaveWebhookConfig：注入参数变化时 syncWebhookWorkloads()——对 svc://
        集群 upsert ConfigMap（msre-pilot-config，不触碰意图 key）并 rollout
        restart Deployment（env 不会热更，重启加载；值未变不滚动）
  - GovernanceTab.vue：回调地址 placeholder 提示双格式
  - 资源命名统一 msre-pilot 系（MWC msre-pilot-inject、entry name
    msre-pilot.oneops.cn、回调路径 /webhook/msre-pilot）；注入 label 族
    （oneops-arthas-injection 等）是对外协议保持不变（demo2 兼容）

- 证书生命周期（rotator.go，借鉴 OtelPilot cert.go 单进程精简版，完全自签自管理）：
  - 首次：Secret 空/占位 → 自动签发（ECDSA P256，CA 10 年 + leaf 10 年，
    SAN=Service DNS）写回，进程等 kubelet 同步（≤5min）后起 TLS server
  - 巡检：12h 一轮 + 启动抖动 0-5min（多副本错峰），leaf 剩余 <30 天自动轮转；
    CA 剩余 ≥60 天复用仅重签 leaf，否则重建 CA；resourceVersion 乐观锁防并发双写
  - 接管：非本体系证书（无 ca.key，如手工 openssl 预置）即使仍在有效期也重建全套，
    不留手工证书路径
  - 跟随：签发/轮转后同步 MWC（msre-pilot-inject）caBundle（漂移自愈）；
    MWC 不存在则跳过（平台启用时读 Secret 最新 ca.crt）
  - 生效：轮转后进程退出由 K8s 重启加载（10 年一轮，重启可接受）
  - 权限：Role（本 ns secret get/update，限定 msre-pilot-tls）
    + ClusterRole（MWC get/update，限定 msre-pilot-inject）
- 验证：backend3 与 arthas-webhook 双工程 go build ./... + go vet exit 0
