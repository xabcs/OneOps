# OneOps 按功能模块分层方案（修正版）

## 📊 实际业务模块重新分析

基于代码深入分析，发现之前的方案存在问题。以下是**修正后的模块划分**：

---

## 🔍 核心发现

### 1. CMDB 和堡垒机是同一个模块

**证据**：
```go
// routes/cmdb_routes.go
func SetupCMDBRoutes(
    r *gin.Engine,
    cmdbController *controller.CMDBController,
    bastionController *controller.BastionController,  // ← 堡垒机控制器作为参数
    ...
) {
    cmdb := api.Group("/cmdb")
    // ...
    cmdb.POST("/servers/:id/connect", bastionController.ConnectServer)  // ← 堡垒机功能在 CMDB 路由下
    cmdb.GET("/sessions", bastionController.GetSessions)              // ← 会话管理在 CMDB 路由下
}
```

**关系图**：
```
CMDB 模块（资产管理）
├── 基础资产管理
│   ├── 服务器管理
│   ├── 凭证管理
│   ├── 标签管理
│   └── 业务组管理
└── 堡垒机功能（服务器连接）
    ├── SSH 连接
    ├── 会话管理
    ├── 终端日志
    └── 权限检查
```

### 2. IAM 就是系统管理模块

**证据**：
```go
// routes/system_routes.go
func SetupSystemRoutes(
    r *gin.Engine,
    menuController *controller.MenuController,       // ← 菜单管理
    roleController *controller.RoleController,     // ← 角色管理
    userController *controller.UserController,     // ← 用户管理
    attributeController *controller.AttributeController, // ← 属性管理
) {
    system := api.Group("/system")
    system.GET("/menus", menuController.GetMenus)
    system.GET("/roles", roleController.GetRoles)
    system.GET("/users", userController.GetUsers)
    system.GET("/attributes", attributeController.GetAttributeDefinitions)
}
```

**IAM 模块组成**：
```
系统管理模块（IAM）
├── 用户管理
├── 角色管理
├── 菜单管理
├── 属性管理
└── 路由管理
```

### 3. 授权中心是独立模块

**证据**：
```go
// routes/auth_routes.go
func SetupAuthRoutes(
    r *gin.Engine,
    applicationPermissionController *controller.ApplicationPermissionController,
) {
    system := api.Group("/system")
    // 应用管理
    system.GET("/applications", applicationPermissionController.GetApplications)
    // 用户组管理
    system.GET("/auth-groups", applicationPermissionController.GetAllAuthGroups)
    // 权限查询
    system.GET("/user-permissions", applicationPermissionController.GetUserEffectivePermissions)
}
```

**授权中心模块**：
```
授权中心模块
├── 外部应用管理（GitLab、Jenkins、JumpServer）
├── 应用权限同步
├── 用户组管理
└── 权限矩阵查询
```

## 📊 修正后的模块对比

### CMDB + 堡垒机合并

**原因**：
- 堡垒机是为 CMDB 服务器提供连接服务的
- 会话管理是基于服务器 ID 的
- 权限检查是基于服务器资产的
- 路由前缀统一为 `/api/v1/cmdb`

**模块结构**：
```
internal/cmdb/
├── domain/
│   ├── server.go              # 服务器模型
│   ├── credential.go           # 凭证模型
│   ├── session.go              # 会话模型
│   ├── policy.go               # 访问策略
│   └── business_unit.go       # 业务组
├── service/
│   ├── server_service.go
│   ├── credential_service.go
│   ├── bastion_service.go     # SSH 连接
│   ├── session_service.go    # 会话管理
│   └── ws_terminal_service.go # WebSocket 终端
└── handler/
    ├── server_handler.go
    ├── credential_handler.go
    ├── session_handler.go
    └── websocket_handler.go
```

### System = IAM

**原因**：
- 用户、角色、菜单、权限都是系统管理的核心功能
- 路由前缀统一为 `/api/v1/system`
- 这是传统的 IAM（Identity and Access Management）模块

**模块结构**：
```

├── domain/

│   ├── role.go               # 角色模型
│   ├── menu.go               # 菜单模型

│   └── route.go              # 路由模型
├── repository/
```

- IAM 和 Authorization 混淆

**现在**：
- CMDB 包含堡垒机（功能扩展）
- System 就是纯粹的 IAM 模块
- Authorization 独立处理外部应用权限

### 2. 符合业务语义

**模块命名与业务功能一致**：
- `cmdb` - 资产管理（含堡垒机）
- `system` - 系统管理（IAM）
- `authorization` - 授权中心（外部权限）
- `k8s` - Kubernetes 管理
- `monitoring` - 监控告警
- `audit` - 审计日志

### 3. 路由前缀规范

**统一路由前缀**：
- `/api/v1/cmdb` - CMDB 模块（含堡垒机）
- `/api/v1/system` - 系统管理模块（IAM）
- `/api/v1/system/applications` - 授权中心模块

- `/api/v1/audit` - 审计模块

## 🎯 总结

### 关键发现

1. **CMDB = 资产管理 + 堡垒机**
   - 堡垒机是 CMDB 的功能扩展，不是独立模块
   - 会话管理基于服务器 ID
   - 权限检查基于服务器资产

2. **System = IAM**
   - 用户、角色、菜单、权限管理
   - 这是传统的 IAM 模块
   - 路由前缀统一为 `/api/v1/system`

3. **Authorization 是独立模块**
   - 外部应用权限管理
   - GitLab、Jenkins、JumpServer 集成
   - 有独立的业务逻辑和数据模型

### 修正后的优势

1. ✅ **模块边界清晰** - 每个模块职责单一
2. ✅ **符合业务语义** - 模块命名与功能一致
3. ✅ **便于维护** - 相关功能集中管理
4. ✅ **降低复杂度** - 减少模块间依赖
